## 11. PDF Export Error — Diagnose and Permanently Fix the Root Cause

**Priority: Critical.**

**Scope:** The `Preview` screen's export workflow and the corresponding `Resume Export` screen.

The actual error shown in the screenshot is:

Title: `PDF request issue`

Message:

`The saved document changed. Review the current Preview before creating a new export.`

The same message also appears below the `Preview & Export` button after returning to Resume Export.

The user encounters this while trying to export a resume. Their available balance is 5 Credits, and the screen indicates a new PDF costs 2 Credits.

**Do not simply hide this message, weaken the validation, automatically retry indefinitely, or bypass the export safety checks. Identify exactly why the saved document is considered changed.**

### Required investigation

Trace the entire export flow through the current implementation:

1. The source of the user's resume data.
2. The authoritative Supabase-saved profile/document state.
3. The save operation and confirmation returned to the client.
4. The document/profile revision, version, fingerprint, hash, or snapshot used to build the preview.
5. The data sent in the export request.
6. The backend validation comparing the current saved document with the preview/export request.
7. Any asynchronous save, refresh, canonicalization, serialization, normalization, or state update that can cause a mismatch.
8. Any client-side recovery cache or persisted local draft that could incorrectly participate in the comparison.
9. The export reservation/idempotency state and its interaction with document versions.

Identify and report the **specific root cause found in the code and/or reproducible test**, not a guess.

### Cloud-first requirement

Supabase must remain the authoritative source for saved profile data.

- Do not treat a separate local profile copy as an alternative saved version.
- Do not export from stale local data when the authoritative saved document differs.
- Do not silently synchronize an outdated local profile over newer cloud data.
- Do not remove or bypass the server's integrity/version checks simply to make the error disappear.
- Preserve temporary interrupted-edit recovery only where required by the existing approved specification; recovered edits must not be treated as saved until explicitly saved successfully.
- A deliberately discarded edit must not be restored or synchronized later.
- Do not delete existing user data or reset the user's profile as a workaround.

### Correct behavior

After a user edits and saves a profile:

1. Wait for the authoritative save to complete.
2. Ensure the preview corresponds to the confirmed saved document/revision.
3. Use the correct authoritative revision or snapshot when requesting the PDF.
4. If the document changes legitimately between preview and export, refresh/rebuild the preview safely and explain what happened without losing edits.
5. Do not repeatedly show the same stale-state error after the underlying mismatch has been resolved.
6. Avoid duplicate export requests, duplicate reservations, and duplicate Credit charges during retries.

Add a focused regression test that reproduces the original failure before the fix and proves the corrected flow afterward.

Also test concurrent or stale document changes so legitimate integrity protection still works.

### Credit safety

- Never charge 2 Credits merely because the request was attempted.
- Preserve the existing reservation, finalization, release, and idempotency mechanisms.
- Charge only when a new PDF export succeeds according to the established backend contract.
- Release or reconcile failed reservations correctly.
- Existing valid PDF downloads must remain free.
- Do not perform a live PDF export or debit Credits during automated testing.

In your final report, explicitly state:

- The root cause.
- The exact code path or condition responsible.
- The fix implemented.
- The regression test that verifies the fix.
- Whether any backend/configuration issue remains.
