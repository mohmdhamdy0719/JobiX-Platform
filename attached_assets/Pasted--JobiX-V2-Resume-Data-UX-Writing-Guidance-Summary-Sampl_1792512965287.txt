# JobiX V2 — Resume Data UX, Writing Guidance, Summary Samples & Persistent Drafts

Act as a senior Flutter engineer, product designer, and UX writer working on the existing JobiX V2 application.

Implement the following improvements to the existing data-entry screens and Resume Layout experience. The goal is to help users provide stronger career information, understand how their information will appear in a Resume, and safely save incomplete entries without accidentally publishing incomplete information to their Resume.

This is an implementation task, not a proposal-only task. Inspect the existing architecture first, then implement the scoped changes and test them.

## 0. Non-negotiable rules

1. Inspect the existing implementation, models, repositories, Supabase schema, RLS policies, migrations, localization, widgets, and tests before editing.
2. Reuse the existing architecture and components wherever possible. Do not create duplicate data models, repositories, or competing persistence mechanisms.
3. Supabase remains the authoritative source for persisted user data. Do not introduce a separate local-only persistent draft system that competes with the server's saved state.
4. Do not change Production, deploy, apply remote migrations, alter IAM, change billing, or modify infrastructure.
5. Do not run PDF exports or perform billable operations during tests.
6. Do not change the Credit system, export pipeline, AI backend, authentication, or unrelated business logic.
7. Do not claim that AI improvement is functional. The existing “Improve with JobiX” feature remains non-functional until separately implemented.
8. Preserve Arabic and English localization, RTL/LTR behavior, accessibility, existing saved records, and current Resume Layout behavior.
9. All user-facing text specified below is product copy approved by the product owner. Use it verbatim in English and provide accurate Arabic localization consistent with the existing localization conventions.
10. Do not invent success messages. A save is successful only after the authoritative persistence layer confirms it.
11. If draft persistence requires a schema change, first inspect the existing schema and migration history. Implement the required migration file and tests, but do not apply it to any remote environment. Report the exact migration and deployment requirement.
12. Keep the changes focused on the requested scope. Do not redesign the entire application.

## 1. Fix Android download cancellation

### Current problem

When a user initiates PDF download, Android opens the file-save/location picker. If the user chooses a location and then presses Back or cancels the picker, the application displays an Android-related error message.

### Required behavior

- Treat a user-initiated cancellation as a normal outcome, not as a failure.
- Dismissing the picker, pressing Back, or cancelling the save operation must not show an error dialog, error snackbar, or alarming failure message.
- Do not mark the download as failed merely because the user cancelled the destination picker.
- Do not delete an existing PDF, trigger a second export, or charge Credits because the picker was cancelled.
- Keep genuine errors visible when an actual download, file write, permission, or storage operation fails.
- Do not broadly suppress Android exceptions. Distinguish cancellation from genuine failure using the existing native/API contract and the actual exception or result type.
- Preserve the current successful download behavior, including filename sanitization and file integrity checks.

### Acceptance criteria

1. Successfully saving a PDF still works.
2. Opening the picker and pressing Back produces no error message.
3. Explicitly cancelling the picker produces no error message.
4. A genuine file-write failure still produces a clear, localized error.
5. Cancelling the picker does not initiate another PDF export or alter Credits.
6. Add or update tests for the cancellation path and genuine failure path wherever supported.

## 5. Add persistent Draft support for incomplete career entries

This is a data and persistence feature, not merely a UI change.

Users must be able to start an entry, save it as a draft when required information is missing, return later to complete it, or explicitly discard it.

Apply this to relevant repeatable career entries, including Work Experience, Education, Volunteer Experience, Projects, and Certifications. Inspect the existing data models to determine the appropriate scope for other sections.

### 5.1 Define completion requirements per entity

Before implementing, inspect the current schema, required fields, Resume renderer, and validation logic.

Define explicit minimum completion rules per entity type. Do not assume that every non-empty field is required.

Examples of minimum requirements to evaluate:

- Work Experience: role/title and organization, plus sufficient identifying information according to the existing model.
- Education: institution and the appropriate degree/qualification or study details according to the existing model.
- Volunteer Experience: role and organization.
- Projects: project title and sufficient identifying information.
- Certifications: certification name and issuing organization where applicable.

Do not invent a universal rule that incorrectly rejects valid records. Dates, descriptions, and optional details should be handled according to the existing product model and the usefulness of the resulting Resume entry.

Document the exact minimum required fields for each entity before finalizing the implementation.

### 5.2 Save behavior for incomplete entries

When the user taps Save:

- If the entry satisfies its minimum completion rules, validate and save it as a complete entry using the existing authoritative persistence flow.
- If the entry does not satisfy those rules, show a confirmation dialog offering:
  - “Save as draft”
  - “Back”

Use this approved English copy:

Title:
“Save as draft?”

Body:
“This entry is missing some essential information. You can save it as a draft and complete it later. Drafts do not appear in your Resume.”

Primary action:
“Save as draft”

Secondary action:
“Back”

“Back” closes the dialog and returns the user to editing without discarding their input.

“Save as draft” persists the incomplete entry and gives the user a clear confirmation only after the persistence layer confirms success.

If the save fails or the connection is unavailable, do not claim that the draft was saved. Preserve the current editing state and provide a clear retry path.

### 5.3 Draft visibility and management

Drafts must be accessible from the relevant section so users can return to them later.

The interface should distinguish complete entries from drafts with clear labels:

- “Draft”
- “Complete”

For each draft, provide an action to continue editing and an explicit discard action.

Before deleting a draft, show:

Title:
“Discard draft?”

Body:
“This draft will be permanently removed. This action cannot be undone.”

Actions:
“Discard draft”
“Keep draft”

Only delete after explicit confirmation.

A draft must not be accidentally deleted by pressing Back while editing. Back should follow the existing discard-unsaved-edits behavior, not silently delete a previously saved draft.

### 5.4 Editing and completing a draft

When the user reopens a draft:

- Restore its saved field values.
- Keep the draft status until the entry satisfies the required completion rules and is explicitly saved as complete.
- If the user taps Save while it is still incomplete, show the draft confirmation again.
- When the user saves a valid complete entry, transition it to Complete only after server confirmation.
- After completion, show it among the completed entries and include it in the Resume renderer.
- Preserve the original record identity where the existing model supports status transitions. Do not create duplicate records when completing a draft.

### 5.5 Critical rule: drafts must never appear in the Resume

Draft entries must be excluded from:

- Resume preview.
- PDF export/rendering.
- Any canonical Resume section data returned for rendering.
- Any Resume layout operation that could expose incomplete draft content.

Enforce this in the authoritative data/rendering layer, not only by hiding draft cards in Flutter.

A draft must never become visible in a PDF just because a client-side filter failed or the user manipulated local state.

Complete entries must continue to render as they do today.

### 5.6 Persistence and architecture requirements

- Inspect the existing Supabase tables, RPCs, RLS policies, repositories, and migration history before choosing the implementation.
- Prefer extending the existing authoritative data model with a persisted status field or another compatible design rather than creating a competing draft store.
- Ensure that users can access only their own drafts.
- Ensure server-side operations and the Resume renderer consistently distinguish drafts from completed entries.
- Keep the current authoritative-save rules, idempotency protections, and retry reconciliation behavior intact.
- Do not treat an uncertain server response as a confirmed save.
- Do not add a local-only persistent draft database that can conflict with Supabase.
- If the existing schema cannot safely support this feature, report the necessary schema/RPC/RLS changes and add a migration file only after establishing a coherent implementation plan.
- Do not apply remote migrations. Report exactly what must be applied to Development before the feature can be considered functional.
- Preserve existing completed entries during any schema transition.

### 5.7 Draft acceptance tests

Add tests that verify:

1. An incomplete new entry cannot accidentally be saved as Complete.
2. The user can choose Save as draft and the persisted status is Draft.
3. The Back action in the confirmation preserves the entered values.
4. A persisted draft can be reopened with its values intact.
5. An incomplete draft remains a draft after reopening.
6. A valid draft becomes Complete only after a successful authoritative save.
7. A failed or uncertain save is not falsely reported as successful.
8. A draft never appears in Resume preview or PDF rendering.
9. Discard requires explicit confirmation.
10. Discarding a draft does not delete any completed entry.
11. Users cannot read or mutate another user's drafts.
12. Existing complete entries, Resume Layout ordering, section visibility, and PDF export behavior remain intact.

Use appropriate unit, repository, widget, and database/RLS tests. Do not run paid export operations during these tests.
