# JobiX — Comprehensive Project Handover, Technical Audit & Production Readiness Documentation

## 1. Mission

Prepare a complete, evidence-based technical handover for JobiX .

I am preparing to continue development using Google Antigravity, and I may return to Replit later. I need the next development environment to understand the actual state of the project without repeating previous work, losing decisions, overlooking unresolved bugs, or assuming unfinished features are complete.

Your task is to inspect the current repository, existing project documentation, implementation, tests, configuration, and available deployment evidence. Then create or update a structured documentation package that accurately records:

- Everything implemented and the latest changes.
- Everything partially implemented or missing.
- Known bugs and unresolved incidents.
- Features and screens requiring review.
- Security vulnerabilities and areas requiring a security audit.
- Backend, database, AI, PDF export/download, billing, Credits, ads, and deployment status.
- Production-readiness requirements and a prioritized execution plan.
- Exact instructions for continuing development in another AI coding environment.

**This is a documentation and audit task, not an implementation task. Do not begin fixing application code during this task.**

## 2. Strict rules

1. Inspect the actual current repository and relevant Git history before writing the handover. Do not rely exclusively on previous chat messages or old reports.
2. Preserve existing architecture decisions and product requirements unless you explicitly document an unresolved concern.
3. Never mark a feature as complete merely because source code exists.
4. Distinguish automated tests, mocked tests, manual device tests, Development deployment evidence, and Production verification.
5. Do not invent test results, deployment states, database migration status, security findings, or successful end-to-end behavior.
6. If something cannot be verified, label it `UNVERIFIED` and state the exact evidence or access needed.
7. Do not run a new PDF export, download a user's file, charge or modify Credits, modify user data, or perform destructive operations.
8. Do not deploy, publish, apply migrations, change cloud infrastructure, modify IAM, rotate credentials, or change Production settings.
9. Never put passwords, access tokens, private keys, service-role keys, signed URLs, or other secrets in documentation. Record configuration variable NAMES and safe setup instructions only.
10. Do not modify application source code, business logic, database schemas, migrations, cloud resources, or deployment configuration.
11. Do not delete existing documentation. Correct outdated documentation only where justified by the actual code and evidence, preserving important historical decisions and explaining discrepancies.
12. Avoid copying huge amounts of source code into documentation. Reference exact repository paths, function names, tests, and relevant Git commits instead.
13. Do not create a new APK unless explicitly requested. APK build details should be documented from available evidence.
14. Do not claim that JobiX is secure, production-ready, or ready for Google Play until the relevant verification has actually occurred.

Inspect the repository structure and identify the actual implementation of:

- Flutter application, routes, screens, shared widgets, state management, and navigation.
- Authentication, user sessions, onboarding, profile management, and account settings.
- Resume creation, editing, preview, layout customization, templates, PDF export, download, and export history.
- Credits, reservations, deductions, refunds, idempotency, usage limits, and transaction history.
- Supabase database, migrations, Row Level Security policies, functions, triggers, Edge Functions, Storage, and authentication configuration.
- Google Cloud services, Gateway, Worker, Storage, IAM, logging, monitoring, and PDF rendering.
- AI providers, prompts, model configuration, server-side AI calls, rate limits, quotas, error handling, and cost controls.
- Advertising integration and any planned monetization.
- Localization, Arabic RTL, English LTR, accessibility, loading states, empty states, and error handling.
- Unit, widget, integration, backend, and security tests.
- Development, Local Preview, and Production configurations, including package identifiers and build variants.
- Google Play configuration, signing, privacy disclosures, subscriptions or purchases if present, and release workflows.
- Existing product specifications, architecture decisions, implementation plans, bug reports, and previous handover documents.

Use actual repository paths and available evidence. If external cloud resources cannot be accessed, document the limitation instead of assuming their state.

## 4. Required documentation files

Create a dedicated folder:

`docs/handover/`

Create the following files. If an equivalent file already exists, update it where appropriate and link to it rather than creating unnecessary duplicates.

### A. `docs/handover/README.md`

The main entry point.

Include:

- Project purpose and high-level architecture.
- Current development status.
- Most important known blocker.
- The order in which the other documents should be read.
- The safest first steps for a developer taking over.
- A prominent warning that Production readiness has not been established unless evidence proves otherwise.

### B. `docs/handover/PROJECT_STATE.md`

A feature-by-feature implementation inventory.

For each feature, include:

- Feature name and user-facing purpose.
- Current implementation status.
- Relevant source files and backend components.
- Existing automated tests and their actual results, if known.
- Whether the feature has been manually tested on a device.
- Known defects and missing behavior.
- External dependencies.
- Exact remaining work.
- Evidence and confidence level.

Use these statuses consistently:

- `VERIFIED` — tested successfully in the relevant environment, with evidence.
- `IMPLEMENTED_UNVERIFIED` — code exists, but real behavior has not been verified.
- `PARTIAL` — some required behavior is missing.
- `BROKEN` — a reproducible failure has been established.
- `NOT_IMPLEMENTED` — required implementation is absent.
- `UNKNOWN` — insufficient evidence to classify.

Do not use `VERIFIED` for a mocked test when real backend or device behavior is required.

- Where PDFs are generated, stored, and downloaded.

- Environment separation and configuration flow.

- Architecture concerns, coupling, single points of failure, and missing observability.

Include Mermaid diagrams where useful, but ensure they represent the real implementation rather than a proposed architecture.

### D. `docs/handover/EXPORT_DOWNLOAD_INCIDENT.md`

This is a critical document. Record the complete history of the unresolved PDF export/download issue.

Include:

- The expected user flow from Export through PDF generation, Storage upload, job completion, signed URL retrieval, direct download, Android save, and opening the saved PDF.
- The actual implementation path and exact relevant source files/functions.
- Confirmed observations versus hypotheses.
- Previous failures and error messages.
- Diagnostic changes made to Flutter and Android code.
- Existing automated test coverage and its limitations.
- Existing APK build results, paths, variants, timestamps, sizes, and checksums when available.
- Backend and Storage evidence already inspected.
- What is still unknown.
- The exact next test required to establish the root cause.
- A safe procedure for capturing `JOBIX_PDF_DOWNLOAD` diagnostics.
- A clear prohibition against logging signed URLs, tokens, PDF contents, or personal information.
- Required regression tests for HTTP errors, timeouts, body interruption, invalid/truncated PDFs, local saving, repeated downloads, and Credit integrity.

Preserve this distinction:

A completed export job does not independently prove that a user successfully downloaded and saved the PDF.

A successful mocked test does not independently prove that the physical Android device can save and open the PDF.

Do not claim that the issue is fixed unless successful end-to-end device verification is documented.

### F. `docs/handover/SECURITY_AUDIT.md`

Create a structured security review of the application.

Inspect, at minimum:

**Authentication and account isolation**

- Can users access or modify another user's profile, resume, files, exports, history, or account data?
- Are ownership checks enforced server-side?
- Are authorization checks consistent across database queries, RPCs, Edge Functions, Workers, and Storage?
- Can object identifiers or request parameters be manipulated to access another user's resources?

**Credits and business logic**

- Can clients forge balances or transaction records?
- Can users bypass server-side checks, reuse requests, manipulate prices, or trigger duplicate deductions/refunds?
- Are Credit operations atomic and idempotent?
- Are retries, concurrency, timeouts, and uncertain outcomes handled safely?
- Can downloading an existing PDF accidentally initiate a new export or charge Credits?

**API and cloud security**

- Are privileged secrets kept server-side?
- Are public endpoints appropriately authenticated and rate-limited?
- Are signed URLs restricted in scope and lifetime?
- Are Storage permissions and IAM roles least-privilege?
- Can untrusted input trigger arbitrary file access, unsafe rendering, injection, or resource exhaustion?
- Are AI prompts and generated content handled safely?

**Privacy and abuse prevention**

- Are personal data and resume contents logged unnecessarily?
- Can users abuse AI usage, export generation, file storage, or advertising flows?
- Are account deletion, retention, and data access flows implemented as required?
- Are error messages leaking internal details?

For each finding, record:

- Severity: Critical, High, Medium, Low, or Informational.
- Status: Confirmed, Suspected, or Not Yet Tested.
- Evidence and affected source paths.
- Realistic impact.
- Recommended remediation.
- Regression test needed.

Do not claim a vulnerability is confirmed without evidence. Do not attempt destructive exploitation or access real users' private data. Do not perform unauthorized penetration testing against Production.

Explicitly list the checks that cannot be completed without a controlled test environment, authorized cloud access, or expert review.
