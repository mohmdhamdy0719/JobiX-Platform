## Objective

Prepare the runner for a future, separately approved Development migration. This task authorizes **local code changes and local/disposable test execution only**.

## 1. Preserve existing behavior

- Inspect the current runner and all existing migration modes before editing.
- Add a new, explicitly named Migration 024 mode.
- Do not change the behavior, defaults, credentials, or target selection of existing modes.
- Pin the target to the existing Development project configuration and retain verified TLS/CA checks.
- Require the exact reviewed migration SHA-256 before any connection attempt.
- Reject Production targets, implicit credential fallbacks, ambiguous modes, and unsafe execution identities.
- Do not expose connection strings, credentials, or secrets in logs.

## 2. Guarded migration flow

Implement the new mode with explicit, fail-closed checks for:

- Confirmed Development target identity.
- Existing migration ledger versions 012–023 and their exact expected checksums.
- Migration 024 absent versus already applied with the exact checksum.
- Conflicting or partially applied schema objects.
- Required table/function/constraint dependencies.
- Table ownership and required permissions.
- Active export/upload activity and relevant lock contention.
- Existing data compatibility, including aggregate checks for incomplete legacy rows.

Do not automatically repair missing migrations, rewrite ledger history, alter permissions, or recover a divergent schema.

Use one transaction for the migration and ledger insertion. Preserve the existing migration advisory-lock convention. Use bounded, fail-fast lock acquisition. If a required assertion fails, roll back the entire transaction.

Before connecting, verify the migration artifact hash and fail immediately on mismatch.

## 3. Local/disposable tests

Create or extend tests so they exercise the new mode without connecting to the real Development or Production database.

Use a disposable local PostgreSQL/Supabase-compatible environment if available. Otherwise, build deterministic mocked-runner tests and clearly identify which database semantics remain unverified.

Test at minimum:

- Hash mismatch fails before connecting.
- Production or unknown targets are rejected.
- Missing or mismatched prior ledger entries abort.
- Migration 024 already applied with the matching hash triggers verification-only behavior, not reapplication.
- A mismatched 024 checksum aborts.
- Conflicting/partial schema aborts without repair.
- Migration SQL failure rolls back both schema changes and the ledger insert.
- Lock timeout aborts cleanly.
- Connection loss around commit is treated as an unknown outcome, requiring read-only ledger/schema inspection before retry.
- Existing runner modes remain behaviorally unchanged.

Do not weaken existing assertions to make tests pass.

- Connect to Development or Production.
