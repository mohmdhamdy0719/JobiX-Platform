# JobiX V2 — Production readiness and cost-efficient launch plan

**Planning only.** No application, SQL, schema, Credits, cloud configuration, gates, retention, deployment or Git history changes were made. No builds or paid workloads were run. Only the existing P0 task’s planning draft was updated.

## 1. Executive assessment

**JobiX is not yet ready for public production.** It has a working development MVP with a recorded personal PDF export/download and substantial local correctness tests. That establishes a useful foundation—not production capacity, operational readiness or a fully verified deployed release.

**Keep Architecture V2**, including the authenticated Gateway/private Worker separation. There is no quantified justification for rebuilding, moving regions or adding infrastructure.

The launch strategy should be:

1. Close specific evidence gaps.
2. Implement and locally verify P0 admission and exception safeguards.
3. Establish operational budgets, security and recovery controls.
4. Run separately approved, budget-capped staging qualification.
5. Release gradually within measured capacity.

## 4. Phased roadmap

All paths below are relative to `mobile/jobix/` unless stated otherwise.

### Phase 0 — Evidence and launch blockers

**Status:** partially documented; current deployment and production evidence unknown.

- **Value:** prevents deploying an inconsistent or unsupported release.
- **Sequence:** reconcile existing evidence → obtain narrowly scoped read-only provider metadata → produce release manifest and blocker register → agree acceptance criteria.
- **Anchors:** root `PROJECT_STATUS.md`, `docs/AI_HANDOFF.md`, `docs/NEXT_STEPS.md`; `backend/pdf/PHASE3_ACCEPTANCE.md`, `Dockerfile`, `package.json`; Gateway, Worker, Edge and migration inventory.
- **Acceptance/definition of done:** every release component has a dated source/configuration reference; each unresolved item has an owner and verification method. No unverified claim is marked passing.

- **Local completion:** documentation/source reconciliation yes; provider facts require read-only evidence.

### Phase 1 — P0 export quotas and exception safety

**Status:** proposed; existing accounting/retry foundation implemented.

**Dependency:** Phase 0 establishes the target baseline.

1. Replace five/ten-minute admission with **1/5m, 3/hour, 5/24h, 10/7d**.
2. Enforce one active intent per user/profile.
3. Propagate authoritative retry-after.
4. Add trusted failure evidence and one-time exceptions after predicate approval.
5. Separately review and implement safe pre-preparation admission/reservation ordering.

- Proposed private failure-evidence/exception records; changes to `jobix_export_finish`, recovery and purge only as necessary.

- `backend/export-gateway/core.mjs`.
- `supabase/functions/resume-export/{transport.mjs,index.ts}`.
- `lib/features/resume/resume_export_panel.dart`.

**Tests/definition of done:** rolling boundaries, real concurrent SQL sessions, same-key replay, single active intent, exception uniqueness, forged/ambiguous evidence rejection, retry-after, deletion races and exactly-once charging pass.

### Phase 2 — Reliability and overload protection

**Status:** queue/retry/fencing implemented; capacity and overload policy proposed/unknown.

**Dependency:** Phase 1 correctness.

- **Value:** absorb bursts without excessive resource spending or stranded reservations.
- **Sequence:** measure queue/worker/DB behavior → choose safe capacity → add bounded queue admission and appropriate backoff → qualify failure-domain circuit breakers → evaluate scaling.
- **Anchors:** `worker.mjs`, `renderer.mjs`, `database.mjs`; `jobix_export_claim`, heartbeat/stage/recover; `export_upload_flights`; Cloud Run effective allocation/concurrency/min/max-instance settings.
- **Acceptance/definition of done:** queue drains inside the reservation deadline with safety margin; no duplicate debit/upload; DB connection use remains below an approved reserve; latency/memory/error targets are measured.
- **Risk/rollback:** higher concurrency can exhaust memory or DB connections. Revert to the last measured capacity; do not increase allocation merely to hide failures.
- **Cost/approval:** local simulation first; cloud benchmarking/scaling requires a separate budget and approval.
- **Local completion:** logic and fault injection yes; real Cloud Run capacity no.

**Three-failure cooldown:** evaluate, do not adopt blindly. Only verified failures in the same service/dependency domain should contribute. Specify a rolling observation window, cooldown, bounded half-open probe and success/reopening rules. User validation errors must not open the breaker. Probe workloads must themselves be authorized.

### Phase 3 — Observability and cost controls

**Status:** provider metrics exist; complete dashboards/budgets/runbooks unknown.

**Dependencies:** Phase 0 billing evidence; Phase 2 capacity informs final budgets. Measurement design can start earlier.

- **Value:** detect overspending and degradation before users lose service.
- **Anchors:** existing Gateway/Worker instrumentation points, admission SQL, queue/reservation/upload-flight tables, GCP Monitoring/Billing, Supabase Usage.
- **Sequence:** define privacy-safe metrics → establish attribution → approve budgets → implement atomic budget admission → validate exhaustion behavior.
- **Acceptance/definition of done:** a synthetic test reconciles admitted work, attempts, reservations and budget consumption; dashboards expose queue age, failure cause, stuck reservations, cleanup lag, preview bytes and cost forecasts.
- **Budget behavior:** **50%** notify/forecast; **80%** investigate; **90%** urgent capacity review; **hard ceiling** stop new work in the exhausted category while preserving accounting, status, recovery and eligible downloads.
- **Risk/rollback:** incorrect counters can block legitimate users. Version policies and preserve reserved completion capacity. Provider caps can interrupt downloads/recovery.
- **Cost/approval/local:** logic tests local; telemetry storage/provider configuration may cost money and needs approval. No previous arbitrary global ceiling is activated.

### Phase 4 — Security, backups, recovery and production operations

**Status:** security mechanisms partially implemented; production acceptance incomplete.

**Dependencies:** Phase 0 inventory and stable Phase 1 interfaces. Security review begins early; its final gate is here.

- **Value:** protect resumes, balances and recovery capability.
- **Anchors:** `supabase/tests/rls.sql`, export SQL tests, privileged RPC grants, Edge authentication, `google.mjs`, `cleanup.mjs`, `ADR-retention-deletion.md`, provider IAM/backup settings.
- **Sequence:** verify authorization and least privilege → review dependencies/images → validate logging/privacy and deletion → rehearse restore and rollback → assign incident ownership.
- **Acceptance/definition of done:** cross-account access denied; no public PDF access; scoped signed URLs; no sensitive payloads in logs; approved RPO/RTO achieved in a disposable restore; reconciliation preserves balances and export state.
- **Risk/rollback:** restored database/object state can disagree. Recovery must handle generation identity, reservations and upload ambiguity before reopening creation.
- **Cost/approval/local:** most authorization fixtures local; restore/provider exercises require explicit environment and cost approval.
- **Separate work:** Task #19, **Grant signup Credits only after verified eligibility, without duplicate rewards**, remains independently reviewed. No historical ledger rewrite.

### Phase 5 — Controlled load testing and release

**Status:** proposed; production capacity unknown.

**Dependencies:** Phases 1–4 passing.

- **Value:** release within demonstrated capacity rather than assumed user counts.
- **Anchors:** existing synthetic PDF fixtures, worker/SQL integration tests, `android/app/build.gradle.kts`, locked dependencies and release manifest.
- **Sequence:** approve staging budget/data → execute bounded load/failure tests → set validated capacity → prepare signed Android release → approve gradual production rollout.
- **Acceptance/definition of done:** approved throughput/latency/error limits met; no financial/data-integrity violations; backup/rollback ready; Arabic/English, RTL, selectable text, A4 layout and preview/export parity pass.
- **Risk/rollback:** stop tests on hard cost/resource thresholds; halt rollout on integrity failures. Revert to a known-compatible release without discarding audit data.
- **Cost/approval/local:** cloud load, signing/build/release and deployment all require separate authorization. No APK or staging workload during planning.

### Phase 6 — Post-launch verification

**Status:** proposed.

**Dependency:** explicit Phase 5 launch approval.

- **Value:** catch workload-dependent failures and prevent premature expansion.
- **Anchors:** release manifest, queue/accounting/cost dashboards, incident and rollback runbooks.
- **Acceptance/definition of done:** reconcile successful exports with debits, review failure/retry amplification, confirm cleanup and budget behavior, and expand only after an agreed observation period.
- **Cadence:** propose daily operational review during initial rollout, weekly cost/capacity review afterward, and review after every release/incident.
- **Risk/rollback:** financial inconsistency, authorization failure or stale-writer resurrection requires immediate containment of new work; preserve recovery/download paths where safe.
- **Cost/approval/local:** real production observation is required; cohort expansion and any new spending need approval.

## 5. Cost model and measurement plan

**Do not use the Iowa sensitivity totals or assumed $25.14 baseline as actual bills.**

Separate:

| Category | Evidence required |
|---|---|
| Fixed platform/database | Actual Supabase subscription, compute/add-ons, shared credits and other project allocations. |
| Export compute | Regional CPU/RAM/request SKUs, billing mode, effective minimum instances, billed allocation and successful/failed attempt duration. |
| Storage | Active/recoverable PDF bytes; selected GCS SKU; total DB growth, allocated disk, WAL and backup usage. |
| Egress/downloads | Run↔Supabase/GCS transfer and destination-specific user download bytes/rates. |
| Failures/retries | Attempt count, duration and cost by outcome—not just successful jobs. |
| Free preview | Preparation CPU, DB calls, response bytes and request volume. |
| Future AI | Approved operation contract, actual token distribution and applicable model pricing; currently no operational usage baseline. |

### Cost per 1,000 operations

For a defined observation period:

- **Incremental export cost/1,000 successes**  
  `1,000 × attributable export cost, including failed/retried work ÷ successful exports`
- **Fully allocated export cost:** show fixed-cost allocation separately, with its allocation rule.
- **Preview cost/1,000 requests:** calculate separately; report success rate and bytes/request.
- Avoid double-counting shared preparation and shared instance time.
- Record region, workload mix, discounts, measurement window and uncertainty.

**Storage measurement:** two aggregate samples around naturally occurring authorized exports, including relation/index/TOAST sizes and total DB/provider disk usage. Account for unrelated writes and maintenance. The three-snapshot 0.99 MB mean remains a small-sample illustration, not a dependable forecast.

## 6. Reliability and capacity criteria

Use local fixtures first, then separately approved staging tests.

Test:

- Short/long English and Arabic resumes, fonts, RTL and images.
- Cold and warm starts.
- Increasing concurrency and bounded bursts.
- Worker termination, lease loss, lost responses and dependency slowdown.
- Upload ambiguity, deletion races and recovery.
- Free preview and download traffic alongside rendering.

A capacity level qualifies only when:

- **Zero** duplicate debits, cross-user disclosures or stale-worker finalizations occur.
- Queued jobs complete or safely terminate before their reservation deadline.
- Queue age returns to baseline after a burst.
- CPU/memory/DB connections retain an approved safety margin.
- Measured p95/p99 latency, failure rate and cost stay within owner-approved targets.

No numerical throughput claim or concurrency increase is justified yet. Avoid cross-user private-content caches; evaluate Chromium reuse only with proven isolation and lifecycle cleanup.

## 7. Security, recovery and release checklist

Before launch, require evidence for:

- Server-derived identity; owner checks; RLS and privileged RPC least privilege.
- Private Worker/GCS and generation-bound, expiry-capped signed URLs.
- No secrets, resume content or full signed URLs in logs.
- Supported runtime and reviewed dependency/image findings.
- Consistent source, migrations, image digests and deployed revisions.
- Production environment and credential separation.
- Confirmed-eligible signup grants with non-destructive backfill.
- Accurate retention wording: seven-day availability is not guaranteed day-seven physical erasure.
- Backup/PITR configuration, restore proof and approved RPO/RTO.
- Named operators, alerts, incident response and tested rollback.
- Proper Android release signing, environment configuration, permissions, privacy/store declarations and Arabic/English device checks.
- AI and unapproved reward features remain inactive.
