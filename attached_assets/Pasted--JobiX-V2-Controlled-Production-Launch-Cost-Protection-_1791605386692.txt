## 3. Weekly cost protection — initial hard ceiling of $10

I want a configurable weekly spending ceiling, initially **USD $10 per rolling seven-day period**, covering the billable resources that JobiX actually uses.

The limit must be centrally configurable so it can be raised as usage grows, without changing the application code unnecessarily. Keep separate configuration for the ceiling, warning thresholds, accounting window, and enforcement behavior.

### Required behavior

- Measure or conservatively estimate cost from server-side usage and the actual provider/SKU pricing applicable to the deployed regions.
- Include relevant billable resources such as PDF rendering, Cloud Run, database/hosting, storage, network transfer, retries, and any AI provider usage that is later explicitly enabled.
- Do not assume that an application-side counter equals the provider's actual invoice.
- Provider billing exports can be delayed. Therefore, use an application-controlled usage budget and conservative cost estimates for immediate protection, then reconcile it with provider billing data when available.
- Prevent new expensive work before starting it if the remaining safe budget is insufficient.
- When the enforced weekly budget is exhausted, reject new billable operations with a stable machine-readable error such as `SERVICE_UNAVAILABLE` and a safe user-facing message: **“Service is temporarily unavailable. Please try again later.”**
- Return a meaningful retry time when it can be calculated reliably. Do not promise that service will resume at an exact time if billing data or accounting windows are uncertain.
- Keep existing valid PDF downloads, job-status queries, account deletion, and essential recovery/accounting operations available where safely possible.
- Do not abandon accepted jobs, leave Credit reservations stranded, double-charge users, or lose track of jobs because the budget was reached.
- If an operation has already been accepted, follow a defined safe completion/recovery policy. Do not blindly kill workers in a way that corrupts state or causes repeated expensive retries.
- Apply the budget to every relevant billable entry point, not just the mobile UI or a single API route.
- Make enforcement atomic under concurrent requests. A burst of simultaneous requests must not bypass the remaining budget.
- Prevent an exhausted or unavailable accounting system from silently allowing unlimited new spending. Define a safe fail-closed policy for new expensive work while preserving essential recovery and valid downloads.

### Configuration and safeguards

Use a centralized, server-side configuration or budget table with appropriate access controls. Avoid hardcoded limits scattered across the codebase.

The initial weekly ceiling is $10. The threshold percentages and alert delivery mechanism should be proposed briefly and implemented only after the underlying cost accounting is trustworthy. Do not invent a notification provider or add paid infrastructure without approval.

Before implementation, identify which services can be gated immediately and which provider costs cannot be measured accurately in real time. Propose the smallest safe implementation that provides an enforceable application-level ceiling and clearly documents any unavoidable billing-delay exposure.

**Do not claim that a $10 cap guarantees the provider invoice can never exceed $10** if committed capacity, delayed billing, background jobs, or other charges can exceed the application’s control. Quantify these limitations and propose practical safeguards.

## 4. Export and Credits correctness

Implement and validate the previously approved export policy:

- Maximum 1 new logical export per rolling 5 minutes.
- Maximum 3 per rolling hour.
- Maximum 5 per rolling 24 hours.
- Maximum 10 per rolling 7 days.
- One active export intent per user/profile.
- A replay using the same idempotency key returns the original logical operation and must not create another quota count or Credit debit.
- An internal retry uses the same job/reservation and does not create a second logical export.
- “Export Again” is a new logical export and counts against quotas.
- A rejected request that was never accepted must not be counted as an accepted logical export or charged.
- Accepted failures count toward quotas by default, even when the reservation is released.
- An automatic quota exception is permitted only when objective, testable server-side evidence proves an internal JobiX failure. Ambiguous outcomes must not qualify.
- A terminal FAILED job remains FAILED. If a verified exception is granted, the user must explicitly create a new operation with a new idempotency key. The replacement counts normally and costs 2 Credits on success.
- New Resume PDF export costs 2 Credits, with reservation and final debit handled atomically and server-side.
- Failed exports release their reservations. Existing valid downloads cost 0 Credits.
- Profile deletion/purge must not accidentally erase the recent history needed to enforce rolling quotas. Propose a minimal privacy-conscious solution before changing deletion semantics.

Inspect the current implementation first. The existing SQL limit may differ from the policy above; do not assume the approved quotas are already deployed.

Do not implement speculative global spending budgets for unrelated categories, automatic failure exceptions, or a new pre-render reservation lifecycle in the same increment unless separately approved.
