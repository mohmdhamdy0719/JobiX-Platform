# JobiX V2 — Fix the Actual PDF Download Failure End-to-End

## Objective

Fix the existing Android PDF download flow in JobiX V2.

**The PDF exists in Google Cloud Storage, the supplied export jobs are marked `COMPLETED`, their recorded PDF size is 154,591 bytes, and the Worker reports no job error. However, downloading the PDF through the Android app fails.**

Available evidence does NOT establish Google Cloud Storage as the root cause:
- The Worker verifies the uploaded PDF before marking the job complete.
- Gateway/Worker responses and IAM `SignBlob` calls succeeded near post-completion activity.
- The observed HTTP 520 occurred before the first relevant job was created and does not explain these failures.
- Available logs do not show the direct Storage GET response, the actual bytes received by Android, or whether local file saving succeeded.
- The app maps multiple different failures to the same generic error message.
- Database completion records do not independently prove current object availability or successful Credit settlement.

Do not assume the failure is in Storage, URL signing, Flutter, Android file saving, or the Worker until the relevant evidence identifies the failing stage.

## Non-negotiable safety constraints

1. Do not trigger a new PDF export during diagnosis.
2. Do not consume, reserve, refund, or otherwise modify user Credits for diagnostic testing.
3. Do not delete, regenerate, overwrite, or alter the existing PDF.
4. Do not deploy to Production, change Production configuration, apply database migrations, change IAM permissions, or modify cloud infrastructure without my explicit approval.
5. Do not expose signed URLs, access tokens, service credentials, PDF contents, or other secrets in logs or reports.
6. Do not repeatedly rebuild the APK without first identifying a code change justified by evidence.
7. Preserve the existing idempotency, authorization, ownership checks, and Credit accounting behavior.
8. Do not claim that the problem is fixed merely because static analysis or unit tests pass.

## Phase 1 — Trace the existing download path

Inspect the actual checked-in implementation and document the complete path used when the user taps Download on an already completed export:

Android UI → Flutter download service → Supabase `resume-export` invocation → Gateway/Worker, if involved in obtaining the download URL → signed URL generation → direct HTTPS GET to Google Cloud Storage → response validation → Android/local file saving → success or error displayed to the user.

Identify the exact functions, files, timeout settings, exception handlers, HTTP status handling, and state transitions involved.

Specifically verify:

- Whether a completed export retrieves an existing PDF or accidentally initiates new export work.
- Whether the signed URL is generated for the correct existing object and remains valid when the direct GET occurs.
- Whether the URL is passed to the HTTP client correctly without being logged.
- Whether redirects, response headers, HTTP status codes, streaming, and binary response handling are correct.
- Whether the app expects JSON when the response is actually PDF bytes, or vice versa.
- Whether HTTP errors, timeouts, connection failures, empty responses, partial downloads, and local save errors are distinguishable.
- Whether the app can incorrectly report failure after the file has already been saved.
- Whether a UI lifecycle, temporary file, Android storage API, or permission issue can cause the failure.
- Whether the current generic error discards useful information from an underlying exception.
- Whether the 30-second direct-download timeout and the 50-second Supabase invocation timeout are appropriate for their respective operations. Do not change them without evidence.

## Phase 3 — Identify and fix the proven root cause

Use the evidence to classify the failure into the actual failing stage:

A. Existing export metadata or URL retrieval.

B. Signed URL validity, expiration, object path, or authorization.

C. Direct HTTP GET or Storage response.

D. Response streaming, binary handling, truncation, or timeout.

E. Android/local file writing, permissions, or file destination.

F. Post-download validation, UI state, navigation, or error mapping.

Fix only the demonstrated cause, including any directly necessary related issue.

Replace misleading generic error handling with safe, actionable error categories. Keep technical details in diagnostics and show the user a clear message appropriate to the failure. Never show a signed URL or sensitive internal error.

The download flow must:

- Reuse the existing completed PDF.
- Never initiate another export just because downloading failed.
- Never charge Credits for downloading an existing valid PDF.
- Preserve the original completed export and its Credit transaction.
- Validate the HTTP response and received bytes before reporting success.
- Avoid reporting success for a partial or empty file.
- Handle retries safely without duplicate export jobs or Credit charges.
- Report a local-save failure distinctly from a server or network failure.
- Avoid deleting a previously valid local PDF because a subsequent retry failed.

Do not rewrite the entire export architecture unless the evidence proves that a broader change is necessary.
