# JobiX V2 — Local-Only Drafts, Offline Editing, Save Reconciliation, and Data-Entry UX

## A. Required Draft and Save Behavior

### Core rule

Incomplete or offline-only edits must remain local to the device. They must not be persisted as server-side Profile Entry Drafts.

A local Draft:
- Exists only on the current device.
- Is not synced to another device.
- Does not count toward Profile Completeness.
- Does not appear in the Resume or PDF.
- Can be edited and explicitly saved later.
- May be lost if the app is uninstalled or its local data is cleared. Make this limitation clear to users when relevant.

Only a complete entry explicitly saved while online may become authoritative server data, and only after the server confirms success.

### Required behavior matrix

1. **Online + complete entry**
   - Validate required fields.
   - Submit the normal server save.
   - Show success and update the Resume/Profile Completeness only after authoritative server confirmation.

2. **Online + incomplete entry**
   - Keep it as a local Draft.
   - Show a clear `Draft` state.
   - Do not send an entry-creation or entry-update request to the server.
   - Do not include it in the canonical Resume snapshot, PDF source, or Profile Completeness.
   - Let the user continue editing and explicitly save after completing required fields.

3. **Offline + complete or incomplete entry**
   - Save the pending edits locally as a Draft, including complete-looking entries that cannot currently be uploaded.
   - Clearly tell the user that the changes are stored on this device only and have not been saved to their account.
   - Do not attempt to claim server success.
   - Once connectivity is available, the user can reopen the Draft and explicitly press Save. Revalidate required fields and submit the normal server save.
   - Do not silently upload Drafts merely because connectivity returns.

4. **Existing Complete entry edited into an invalid/incomplete state**
   - Never reclassify or overwrite the authoritative Complete entry with a Draft.
   - Preserve the existing protection: show validation feedback, send no save request, and leave the saved server entry unchanged.
   - The user may discard their pending edits or restore the required fields.
   - Reopening the saved entry must load the confirmed server version.

5. **Personal Information**
   - Do not create server-side Draft records for Personal Information.
   - When offline, preserve pending changes locally without changing authoritative server data or server-derived Profile Completeness.
   - Clearly distinguish locally pending changes from account-saved information.
   - On reconnection, require an explicit Save action to upload the pending changes.
   - Preserve the existing account/profile isolation and version checks.

### Local persistence and privacy

Inspect the current local persistence mechanism and use the smallest appropriate existing solution. Local Drafts must be scoped to the signed-in account and the relevant profile/section to prevent cross-account or cross-profile leakage on shared devices.

Do not introduce a competing persistent canonical profile or allow local Drafts to overwrite fresh server data silently. Distinguish local pending edits from authoritative server records.

Do not silently delete pending data during sign-out. Follow the existing sign-out safety behavior, explain what will be lost, and require the appropriate user confirmation.

### Fix the current uncertain-save error safely

The app currently displays:

`The previous save result is not yet confirmed. Retry the save before discarding; already-saved server data cannot be undone`

Investigate the actual call path, request lifecycle, idempotency key, retry behavior, and discard flow before changing it.

The intended experience is that ordinary local Drafts and ordinary unsaved edits should not produce this server-save uncertainty message.

However, do not simply remove the message or discard an unresolved server request. A request that may already have reached the server must retain its original idempotency key and payload until its outcome is reconciled. Never issue a duplicate logical save with a new key, and never claim failure or success without evidence.

Correctly distinguish:
- A purely local Draft with no server request.
- An ordinary unsaved edit.
- A confirmed server save.
- A server request whose outcome remains uncertain.

Only the last case should require the existing reconciliation/retry protection. Resolve the underlying state-transition bug responsible for the current erroneous message.
