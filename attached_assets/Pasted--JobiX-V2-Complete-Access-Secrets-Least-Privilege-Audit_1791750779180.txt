# JobiX V2 — Complete Access, Secrets & Least-Privilege Audit

## Objective

Before proceeding with Migration 021, deploying or updating the PDF Gateway/Worker, or performing a live PDF export, conduct a complete, evidence-based audit of all credentials, tokens, service accounts, IAM roles, database privileges, and external access used by the JobiX development workflow and deployed application.

The goal is to give Replit and each runtime component only the permissions actually required for their responsibilities, while preserving development functionality, security, privacy, and recovery options.

This is an audit and recommendation task only. Do not implement changes.

## 1. Inventory every credential and secret

Inspect the repository, workspace configuration, Replit Secrets configuration where accessible, deployment configuration, scripts, and service definitions.

Identify every credential by:
- Secret/environment-variable name.
- Credential type and provider.
- Where it is configured and which code/scripts consume it.
- Whether it is used locally, by Replit during development, in CI/build/deployment, or by a deployed runtime service.
- The exact operations it enables or is expected to enable.
- Whether the credential is currently required, redundant, overly privileged, unused, or impossible to verify.
- The proposed least-privilege replacement, if applicable.

Include at least:
- Supabase publishable/anon keys, secret/service-role keys, database connection credentials, access tokens, and any personal access tokens.
- Google Cloud credentials, deployer credentials, service-account keys, Application Default Credentials, impersonation permissions, and CI/deployment identities.
- Cloud Run Gateway and Worker runtime identities.
- Artifact Registry, Cloud Build, Cloud Storage, and Scheduler access.
- Any credentials used for migrations, SQL tests, APK builds, or other deployment scripts.
- Credentials for any additional provider actually used by this repository.

Do not print secret values, tokens, private keys, connection strings, signed URLs, or sensitive payloads. Report names, types, locations, usage, and privilege implications only. If a secret's value is inaccessible, state that explicitly; do not guess.

## 2. Supabase least-privilege analysis

Determine exactly how the application and development tools access Supabase:
- Flutter client authentication and normal user data access.
- Edge Functions and their secrets.
- Gateway authentication and authorization.
- Database migrations and administrative scripts.
- Development/test tooling.
- Any service-role or equivalent elevated access.

For every access path, explain which permissions it needs and why.

Specifically determine whether Replit currently has a Supabase token or key that can perform unrestricted or elevated operations. If so, identify the affected workflows and the risks, without exposing its value.

Recommend which operations should use:
- The publishable/anon key plus authenticated-user RLS policies.
- A narrowly scoped database role or restricted SQL interface.
- A server-only secret available only to the specific trusted runtime that needs it.
- A temporary, explicitly approved migration credential.
- No credential at all.

Do not assume that replacing a service-role key with an anon key is sufficient. Review RLS, grants, SECURITY DEFINER functions, Edge Function authorization, and the actual required operations.

## 3. Google Cloud least-privilege analysis

For project `mhflow-jobix`, region `me-central1`, inspect the repository and any available read-only evidence for:
- Gateway and Worker runtime service accounts.
- Deployer identity and its project/resource-level roles.
- Cloud Run deployment and invocation permissions.
- Artifact Registry push/pull permissions.
- Cloud Build permissions.
- Cloud Storage object permissions on `mhflow-jobix-dev-pdfs`.
- Scheduler permissions, if used.
- Service-account impersonation and service-account key usage.
- Any project-wide roles that could be replaced with resource-scoped permissions.

For every principal, list its current known roles, scope, purpose, required permissions, excess permissions, and proposed minimum replacement.

Distinguish project-level grants from service-level and bucket-level grants. Do not infer effective IAM from repository source alone. Mark live permissions NOT VERIFIED if read-only Cloud IAM evidence is unavailable.

Keep the Worker private. Preserve authenticated Gateway-to-Worker invocation. Do not recommend broad Owner, Editor, Storage Admin, or Cloud Run Admin grants for normal runtime identities when narrower permissions suffice.

## 4. Separate the access profiles

Create a permissions matrix for these distinct identities:

1. Replit development agent.
2. Local developer and migration operator.
3. CI/build/deployment identity.
4. Gateway runtime identity.
5. Worker runtime identity.
6. Flutter application and authenticated end users.
7. Supabase Edge Functions and database roles.
8. Scheduler or cleanup identity, if applicable.

For each identity, specify:
- Read permissions.
- Write permissions.
- Deploy/admin permissions.
- Database privileges.
- Secrets it may access.
- Resources it must never access.
- Whether access should be permanent, temporary, or approval-gated.

Replit must not automatically inherit production-style administrative access just because it is developing the application.

## 5. Preserve the current safety boundaries

Treat these as hard constraints:
- PDF export remains disabled.
- `accounting_ready=false`.
- All five cost inputs remain unset until separately reviewed.
- Do not apply Migration 021 or any other migration.
- Do not deploy, build/push images, change Cloud Run traffic, or modify IAM.
- Do not create, rotate, revoke, replace, or delete credentials.
- Do not alter Supabase RLS, grants, functions, secrets, or database records.
- Do not run live exports, paid AI operations, or test writes in Development.
- Do not change application code, dependencies, lockfiles, pricing, Credits, or retention.
- Do not expose secret values in logs, output, generated files, or the report.
- Do not use an existing deployer credential to perform read-only inspection.
- Do not claim live cloud settings are verified unless evidence actually establishes them.

You may inspect source code, configuration names, scripts, and available read-only evidence. If an action requires new access, report the exact access needed and stop.

Inspect the diff and relevant tests. Report:
- Exact dependency and lockfile changes.
- Whether the Express major version changed.

- Existing test evidence and remaining gaps.

Do not modify or revert these changes in this task.

## 7. Required deliverables

Return:

A. **Credential inventory** — one row per credential or secret reference, with no secret values.

B. **Supabase permissions matrix** — current known access, actual use, risks, and minimum recommended access.

C. **GCP IAM matrix** — principal, resource scope, known roles, purpose, excess access, and minimum recommended permissions.

D. **Replit access requirements** — a precise list of operations the development agent genuinely needs and which credentials or roles enable them.

E. **Proposed target architecture** — which identities own which operations, which credentials remain server-only, and how temporary administrative access is handled.

F. **Implementation sequence** — safe order for reducing privileges without locking out the project or breaking migrations, deployments, tests, or runtime services.

G. **Verification checklist** — how we can prove each change worked without enabling PDF export.

H. **Blockers and unknowns** — explicitly distinguish verified facts, source-only evidence, historical evidence, and unverified live state.

For every recommendation, explain the specific permission or risk it addresses. Avoid generic security advice and avoid repeating unrelated project audits.

Stop after delivering the report. Do not implement any recommendation until separately approved.
