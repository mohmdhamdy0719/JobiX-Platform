BUG 2 — BACK BUTTON MUST NEVER RANDOMLY EXIT THE APP
------------------------------------------

Current behavior is unacceptable:

Pressing Back can exit the application instead of navigating back within the Jobix navigation flow.

We need a consistent Jobix navigation policy.

Required behavior:

A. Inside a nested screen/editor:
- Back returns to the previous Jobix screen.
- It must NOT exit the app.

B. Inside a repeatable entity editor:
- Back returns to its parent list/editor.
- It must NOT save unsaved data.

C. If the user has unsaved changes:
- Back should discard the unsaved draft/edit.
- For existing records with modified unsaved data, use an appropriate "Discard changes?" confirmation if needed.
- Do NOT silently save.

D. On a true root-level screen where there is no previous in-app destination:
- Do NOT immediately exit.
- Show a polished Jobix confirmation dialog such as:
  "Exit Jobix?"
  with appropriate secondary/primary actions.
- The exact wording should follow the established Jobix design system and app language.
- English and Arabic must both be supported.
- The dialog should feel native to the application and not like a browser alert.

E. Android system Back and in-app AppBar Back must follow the same navigation policy.

F. Do not create a patch that only fixes one screen.

Inspect the current GoRouter/navigation architecture and implement a centralized, predictable Back behavior.

Use the correct Flutter modern navigation APIs rather than deprecated APIs.

Add tests covering:
- nested navigation
- root navigation
- editor navigation
- unsaved new entity
- unsaved existing entity
- root exit confirmation
- Android back behavior
- Arabic/English dialog direction

Do not allow the Back button to become a hidden Save operation.

BUG 3 — UNSAVED NEW EDUCATION/ENTITY MUST NOT PERSIST
------------------------------------------

Current bug:

The user opens "Add Education", changes some fields, then presses Back without pressing Save.

The education entry still appears in the parent list.

This violates the required Jobix data semantics.

IMPORTANT RULE:

OPEN / EDIT ≠ SAVE

Only explicit Save may commit an entity.

Required behavior:

NEW ENTITY:
- Opening Add Education creates only an in-memory/local draft.
- Editing fields changes only the draft.
- Pressing Back without Save discards the draft.
- The parent list must NOT show the new entity.
- Pressing Save validates and commits the entity.
- Only after successful Save should it appear in the parent list.

EXISTING ENTITY:
- Opening an existing record loads an editable draft.
- Editing changes the draft.
- Pressing Back does not commit changes.
- If appropriate, show "Discard changes?" before leaving.
- Pressing Save commits changes.

This rule applies consistently to:
- Education
- Certifications
- Achievements
- Work Experience
- Projects
- Languages
- Volunteer Experience
- any future repeatable entity editor

Inspect the current repository/mutation flow carefully.

Do not fix only Education.

Determine whether the bug is caused by:
- parent list state mutation
- shared mutable objects
- optimistic persistence
- Drift writes
- provider state
- route arguments
- draft initialization
- autosave
- repository behavior
- profile.mutate being called too early

Implement the correct draft/commit boundary.

Add regression tests for every repeatable editor pattern.
