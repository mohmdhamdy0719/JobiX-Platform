# JobiX — Final UX Refinement, Data Persistence, and PDF Export Polish

## Objective

We are preparing JobiX for Production. Before starting the ATS Score and AI Generation features, we must resolve the current UX problems, simplify the user experience, and make the existing profile and PDF export flows consistent and reliable.

Act as a senior Flutter engineer, product designer, UX writer, and QA engineer.

Inspect the existing implementation first. Reuse established components and patterns where appropriate. Implement the changes below without unnecessarily rewriting working features.

**Important:** This is preparation for Production, not authorization to deploy to Production or modify Production infrastructure.

## 1. Critical product principle: Cloud-first persistence

The Supabase account data is the single authoritative source of truth.

We do not want users to think about local drafts, cloud copies, synchronization, or competing versions of their information. Local storage is only a temporary recovery mechanism to protect users from unexpected interruptions.

Implement and preserve these principles:

- Saved profile data must be loaded from and persisted to Supabase.
- Local recovery data must never become a second authoritative profile or override newer server data.
- If a user is interrupted while editing, preserve recoverable unsaved input temporarily so they can return and explicitly save it to Supabase.
- If the user deliberately discards the unfinished changes, those changes must not be saved to Supabase or restored later.
- If the user chooses to leave an editing flow with unsaved changes, present a short, clear confirmation that allows them to continue editing, save when possible, or discard their unfinished changes.
- If recovery data exists after an unexpected interruption, restore the editing experience and let the user explicitly save the recovered changes to Supabase. Do not silently treat recovered changes as saved data.
- If the user cannot return to the interrupted editing flow, or deliberately discards the changes, do not persist those changes to Supabase.
- Signing out must not present local recovery as a separate account version. Preserve already-saved Supabase data.
- Do not introduce a general offline mode. JobiX remains an online application; local recovery is only a temporary UX safeguard.

Remove user-facing concepts such as “local draft,” “cloud version,” “review latest saved version,” and “back — retain local draft” wherever they expose internal implementation details.

Do not simply hide these messages while leaving inconsistent data behavior underneath. Review the actual persistence and recovery flow, then implement the smallest safe changes needed.

Do not weaken existing authentication, Row Level Security, authorization, validation, or server-side ownership rules.

## 6. Professional Summary — Improve the question-and-answer guidance

The current collapsible question section is visually poor and difficult to use.

Redesign it as a polished, compact guidance component that helps users understand what to write without overwhelming them.

Use these questions and examples:

1. **What is your professional background?**
   Example: “Marketing specialist with three years of experience in digital campaigns and content strategy.”

2. **What are your strongest skills or areas of expertise?**
   Example: “SEO, campaign analytics, content planning, and stakeholder communication.”

3. **What work or problems do you solve best?**
   Example: “I turn campaign data into practical improvements that increase engagement and conversion.”

4. **What achievements or results are you proud of?**
   Example: “Improved organic traffic by 25% over six months.” Make clear that examples are illustrative; users must enter their own truthful results.

5. **What type of role are you looking for next?**
   Example: “A digital marketing role focused on growth, experimentation, and measurable results.”

6. **What value do you bring to an employer or team?**
   Example: “I combine analytical thinking with clear communication to help teams make better marketing decisions.”

UX requirements:

- Keep the questions easy to scan and expand.
- Use readable typography, appropriate spacing, and clear visual hierarchy.
- Avoid a wall of large bordered accordions.
- Let users consult examples without forcing them to answer every question.
- Do not automatically insert example text into the user's actual resume.
- Keep the actual resume content separate from guidance.

## 16. Preparing Resume screen

The current screen displays an indefinite-looking spinner and a long internal job identifier. Improve it so the user understands the actual export status.

### Progress and status

Display clear status messaging that reflects the real backend state, for example:

- “Preparing your resume…”
- “Generating your PDF…”
- “Your resume is ready.”

Only show a status when it corresponds to the actual state or a known processing stage.

Do not fabricate a percentage, pretend the export is progressing when no progress data exists, or display “Finished” before the server confirms success.

If the backend cannot provide genuine percentage progress, use a clear indeterminate progress indicator and truthful status messaging instead.

If reliable duration data is available, a reasonable estimate may be shown. Do not invent a guaranteed completion time.

### Job identifiers

The current UUID-like identifier is too technical for users.

Keep the full internal job ID unchanged for backend correlation, support, security, and idempotency.

For the user interface, prefer a short, stable numeric reference, such as an 8-digit display reference, if it can be generated and stored safely without collisions or authorization problems. Do not truncate the internal UUID and treat it as a new unique identifier.

Use the actual user's name for the downloaded filename where supported, with a safe filename such as:

`Hamdy_Hassan_Resume.pdf`

Sanitize the filename and use a sensible fallback when the name is missing. Do not expose internal job IDs in the filename.

### Navigation

Review the top-left back control. The user must not be accidentally trapped in a processing flow or sent to an unrelated screen.

Use the simplest navigation that fits the existing flow. If a back control is retained, it should return to a safe, relevant screen without cancelling or corrupting an in-progress export.

The “Return to dashboard” action should return to the Home screen. Keep navigation labels and destinations consistent.

### Performance

Investigate why PDF generation takes as long as it does. Identify measurable bottlenecks before changing implementation.

Optimize only where it is safe and supported by evidence. Preserve export correctness, authorization, output validation, storage privacy, and retry safety.

Do not weaken security controls to make the spinner disappear faster.

1. Inspect the existing navigation, persistence, authentication, resume forms, export flow, and relevant tests.

3. Prefer shared fixes over duplicated per-screen implementations.

After implementing:

1. Run the relevant Flutter analysis and focused widget/unit tests.
2. Run the existing tests for profile persistence, recovery/discard behavior, authentication navigation, Credit accounting, export lifecycle, download expiry, and system-back navigation where available.
3. Verify that valid existing PDFs can be downloaded without additional Credits.
4. Verify that failed exports do not receive a final charge.
5. Verify that an interrupted unsaved edit can be recovered and explicitly saved without creating a second authoritative profile.
6. Verify that deliberate discard does not save or restore the discarded changes.
7. Verify that a completed Profile Creation Journey remains completed after signing out and signing back in.
8. Verify that no unwanted periodic export-history polling remains.
9. Verify the relevant layouts in both English (LTR) and Arabic (RTL).
10. Run `git diff --check` and inspect the final diff for unintended changes.

Do not use real user data as test fixtures. Use fictional data and isolated test accounts where required.
